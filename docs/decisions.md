# Decision log

Format: date · decision · why · alternatives considered.

## D1 — 2026-11-20 · Stack: C++20 sim + C11 firmware, SDL2 + Dear ImGui + ImPlot, MSYS2 UCRT64 at `D:\msys64`
- **Why:** native C/C++ links firmware directly; ImPlot gives fast live plots; GCC matches the arm-none-eabi-gcc used for STM32; MSYS2 pacman provides GCC/CMake/Ninja/SDL2 in one place; D: chosen to save C: space.
- **Installed (2026-11-20):** GCC 16.2.0, CMake 4.5.0, Ninja 1.13.2, GDB 18.1, SDL2 2.32.10, clang-format 23.1.5, Python 3.14.10 (all MSYS2 UCRT64).
- **PATH policy:** persistent system/user PATH is not modified; `cmake/toolchain-msys2-ucrt64.cmake` pins compilers/Ninja under `MSYS2_ROOT` (default `D:/msys64`), so legacy `C:\MinGW` GCC 6.3 is never used.
- **Alternatives:** Qt 6 (heavy, LGPL, slower iteration); raylib (weak UI/plots); Web UI + C++ backend (two codebases); MSVC Build Tools (different compiler family from STM32 GCC).

## D2 — 2026-11-20 · Firmware runs as a DLL in lockstep with sim time
- **Why:** unload/reload gives clean firmware globals on reset and hot-reload after rebuild; lockstep (ISR on sim thread, main loop resumes only at blocking HAL calls) makes runs bit-deterministic.
- **Trade-off:** real ISR-preemption races are not reproduced (documented limitation).
- **Alternatives:** static link into the sim exe (no clean reset of globals); free-running threads (non-deterministic); MCU emulation via QEMU/Renode (out of scope, much slower iteration).

## D3 — 2026-11-20 · Dependencies pinned by archive hash via FetchContent
- doctest 2.5.3, nlohmann/json 3.12.0 (`cmake/deps.cmake`, SHA-256 checked). ImGui (docking) + ImPlot to be added in Slice 2 the same way.
- **Why:** reproducible builds without vendoring; CI and local fetch identical sources.

## D5 — 2026-11-20 · GUI deps, renderer, visual verification, static runtime
- **Deps (Slice 2):** Dear ImGui 1.93.0-docking, ImPlot 1.1, stb @ `6b5799b` (stb_image_write), SHA-256 pinned; SDL2 2.32.10 from MSYS2. Backend: SDL2 + SDL_Renderer (D3D11), per the ImGui `example_sdl2_sdlrenderer2` of the same version.

SDL's `--software` rasterizer leaves a 1-px seam on the diagonal of thin wall quads and drops some ~3-px post squares, so it is diagnostic only. Probes sample a strip across the wall thickness (robust to seams, still fails on any missing/extra wall).

- **Geometry lives in `sim/core/maze_geometry`** (metres; origin = centre of SW post; 180 mm pitch, 12 mm walls) so physics/raycast reuse exactly what is drawn.
- **Amended in Slice 3:** shared libraries (= firmware DLLs, pure C) link only `-static-libgcc`; whole-archive winpthread stays exe-only because a DLL that is `FreeLibrary`'d on every reset should not carry pthread TLS callbacks.
- **Maze text parser follows mms semantics:** any non-space char at a wall position is a wall (`+` or `o` posts); `.maz` = N*N bytes column-major, low nibble only.

## D6 — 2026-11-20 · Firmware main runs on a Win32 fiber; physics model and collision choices (Slice 3)
- **Fiber, not thread.** `fw_main` runs on a fiber (`sim/platform/fiber`); `FirmwareHost` switches to it only at t=0 and when a blocking HAL call's deadline is reached; the SysTick ISR runs on the caller's stack after each 1 ms physics tick. Same lockstep semantics as D2 with a ~1 µs switch instead of 5–20 µs thread hand-offs (needed for the ≥ 50× headless target). Reset = delete the suspended fiber + `FreeLibrary` + load a fresh private copy of the DLL (copy-on-load also allows rebuilding while the sim runs and gives parallel sessions separate globals).
- **Faults:** blocking call inside the ISR → `Faulted` (motors zeroed); `fw_main` returning → `Halted`; a busy-wait polling `hal_millis/micros` yields a tick every 256 reads. A loop with no HAL calls at all cannot be pre-empted: `run_guarded` runs the session on a worker thread and, after a wall-clock timeout (GUI: 2 s), reports `Hung` and abandons that thread + session.
- **Drive model:** DC motor (R, Kt, Ke, gear, rotor/wheel inertia, viscous + Coulomb friction with stiction, efficiency) coupled through the rigid-body mass matrix in wheel-speed coordinates; integrated implicitly in the decoupled sum/difference modes at 0.25 ms, so symmetric inputs give exactly straight lines and exact pivots; pose by exact arc integration. Verified against closed-form solutions (τ within 0.3 %, arc radius 1e-9, zero heading drift over 10 m). Wheel slip: see D7. Terminal voltage = duty × battery, clamped to `motor.max_voltage` (6 V for N20 on 2S) with a counted warning.
- **Collision:** body = oriented rectangle (exactly what is drawn) vs wall/post AABBs (SAT + minimum translation), uniform-grid broadphase, swept sampling ≤ half a wall thickness per sample + 12-step bisection to the last free pose; response zeroes or reverses (×restitution) wheel speeds; one `CrashEvent` per contact begin. No tunnelling at 20 m/s; penetration ≈ 2e-5 mm at 0.8 m/s.
- **arm-check** compiles each firmware to an object with `-O2 -Werror -Wdouble-promotion` for Cortex-M4F (stricter than the planned `-fsyntax-only`, which skips codegen warnings).
- **Alternatives:** OS threads + condition variables (planned in 3.3; too slow per tick); setjmp/longjmp stacks (non-portable stack switching); explicit RK4 (needs smaller steps for the stiff motor pole, no exact symmetry); polygon body (rectangle suffices until a real chassis outline arrives in Phase 2).

## D7 — 2026-11-20 · HAL v2 sensors, deterministic noise, linear tyre slip (Slice 4)
- **HAL v2** (`MMHAL_VERSION 2`, `MMSIM_HOST_ABI 2`): adds `hal_get_encoders`, `hal_get_gyro` / `hal_get_accel` (3-axis structs, body frame x fwd / y left / z up) and `hal_get_distance(ch)` -> mm or `HAL_DISTANCE_NONE` (0xFFFF). v1 calls are unchanged. Channel order for the presets: 0 = left/diag_left, 1 = front_left, 2 = front_right, 3 = right/diag_right. `hal_get_gyro_z_dps` now returns the *measured* rate (noise, bias, quantisation), never ground truth.
- **Sensors** (`sim/core/sensors`): each channel samples on 1 ms tick boundaries at its own `rate_hz`, draws noise **at sample time** from its own stream, and delivers after `latency_ms` - so readings never depend on how often firmware reads them. Beam = `rays` rays across `fov_deg`, weighted `edge_weight^((off/half)^2)` (Gaussian-like profile). ToF = nearest hit in the cone; IR = ambient + weighted mean of `gain * cos(incidence)^p / (d + d0)^2` ADC counts. `hal_get_distance` for IR uses the inverse of that model ("board calibration"), so it is exact for a perpendicular wall and biased at oblique angles, like a real calibrated IR. IR emitters default ON (the board pulses them); `hal_emitter_set(ch, false)` leaves ambient only and distance NONE. Presets `front_side` / `front_diagonal` + per-sensor overrides in JSON.
- **Raycast:** slab-method ray vs wall/post AABBs through the same uniform grid as collision (exact; ray starting inside a box gives t = 0).
- **Noise & PRNG:** `xoshiro256**` per source, seeded `splitmix64(world_seed ^ FNV-1a(stream name))`; Box-Muller without a cached spare. Adding a sensor never changes the other streams; `--seed N` (GUI/CLI) sets the world seed. Distance noise sigma = `noise_sigma + noise_rel * value`, then quantisation. IMU: white noise, constant bias + random-walk bias, quantisation (LSB), range clamp; accelerometer = world velocity change over the tick in the body frame + gravity on z.
- **Encoders:** `floor(angle * CPR / 2pi + 1e-9)` (a decoder counts edges passed; floor, not round), per-side wiring inversion, int32 wrap. CPR = `counts_per_motor_rev * gear_ratio`.
- **Linear tyre slip (Peter Harrison's slip-gradient idea), opt-in** (`slip.enabled`, on in `generic_classic.json`, off in the struct default so Slice 3 results stay exact):
  - Longitudinal: per wheel `F = C (r w - u)` with `u` the contact-patch ground speed, capped at `mu m g / 2`. Body `v`, `w` become states. Backward Euler in the decoupled sum/difference modes (2x2 each, so symmetric inputs stay exactly straight / exactly in place); if a wheel saturates its force is fixed at the limit and the 4x4 system is solved by Gaussian elimination. Result: acceleration capped at `mu g`, wheels spin up and odometry over-reads.
  - Lateral: slip angle `beta = k * a_lat`, `k = slip_gradient_deg_per_g * pi/180 / g`, `a_lat = v w` clamped to `mu g`; the velocity direction `phi = theta - beta` may turn at most `mu g dt / |v|` per step (skid). Pose moves along mid-`phi`.
  - Wall contact with slip: body `v`/`w` are zeroed/reversed (x restitution) and `beta` reset; the wheels keep spinning, so encoders keep counting while pinned (as on a real mouse).
- **Alternatives:** Pacejka magic formula (too many unknown parameters for a generic mouse; linear + cap captures the behaviour that matters for control tuning); per-read noise (makes results depend on firmware polling rate); one global RNG (adding a channel would shift every other stream).

## D8 — 2026-11-20 · Demo firmware design, motor safety in firmware, GUI pacing (Slice 5)
- **`firmware/demo_floodfill/`** (pure C11, mmhal only, ARM-clean): `control.c` 1 kHz ISR (encoder odometry, gyro heading with a 300 ms bias calibration at boot, trapezoidal profiles, PD position loops on per-tick accumulated errors plus motor-model feed-forward per wheel: kV = 4.38 V/(m/s), kA = 0.24 V/(m/s^2), static 0.1 V), `sensors.c` (diagonal wall following, wall thresholds), `maze.c` (BFS flood fill; search = unknown walls open, speed run = known-open walls only), `mouse.c` (moves, search, speed run), `motors.c`, `profile.c`, `main.c` (state machine).
- **Search pattern:** walls of a cell are read at its entry boundary (diagonals see that cell's side walls ~20 mm past its centre; the front sensors see its front wall at ~125 mm). Straight on = keep moving; a turn = stop at the centre, square up on a front wall if there is one (front sensors to 34 mm and equal), turn in place with the gyro, go. Steering stops when a front wall is within 80 mm (the diagonals would see it).
- **Calibration constants** (`config.h`) were measured in the simulator, the way a real robot is calibrated: diagonal 109 mm when centred, 1.68 mm per mm of offset, ~4.2 mm per degree; thresholds 140 mm (side) and 170 mm (front at a boundary).
- **Motor safety lives in the firmware** (`motors.c`), as on the robot: terminal voltage capped at 6.0 V (duty = V / V_battery, never 100 % PWM); every change of direction passes through >= 20 ms at 0 V (time already spent at 0 V counts). The simulator's own `max_voltage` clamp stays as a second line of defence.
- **Results (seed 1):** UK 1987 search 42 s, return 34 s, speed run 21 s, total 97 s simulated, 0 crashes, every mapped wall correct; same for seeds 2-3, three generated mazes and UK 1988/2000/2017. Debug and Release builds give bit-identical runs.
- **Pacing (`sim/host/pacer`):** fractional accumulator, sim ms = speed x wall time with no per-frame rounding drift; frames longer than 100 ms are not caught up (reported as behind); Max runs as many ticks as fit in 12 ms per frame. Measured with `mmsim --live-for`: 60 s at 1x -> 60.006 s simulated in 60.006 s wall; 2x/5x/10x within 0.01 %; Max ~64x (Release, visible window). Headless (Release) runs UK 1987's whole mission at ~135x real time.
- **Deferred:** smooth (arc) search turns and diagonal speed runs - in-place turns are robust and well inside the 5 min budget; cell-colour annotations are sent but drawn only in Slice 6.
- **Alternatives:** stop-at-every-cell search (simpler, ~2x slower); deciding at the cell centre (no time to brake from search speed); absolute heading tracking (front-wall squaring + steering keep relative heading error bounded without it).

## D9 — 2026-11-20 · Telemetry recorder, replay by re-simulation, annotations, GUI controls (Slice 6)
- **Telemetry (`sim/host/telemetry`):** per-channel fixed-capacity ring buffers (time as double, value as float), 60 000 samples per channel (60 s at 1 kHz) and at most 64 channels, so a run of any length uses bounded memory (about 18 MB with 24 channels). The Session samples 17 built-in `sim.*` channels after every tick (v mm/s, w deg/s, x/y m, theta deg, motor V L/R, wheel rad/s, slip beta, measured gyro z, encoder counts, `sim.d.<sensor>` mm, NaN when nothing is in range). Firmware `hal_telemetry` channels go into the same recorder under their own names.
- **CSV:** one row per sample of the clock channel (`sim.v`, 1 kHz) in [t0, t1); every other column is sample-and-hold (empty before its first sample or for NaN). The GUI exports the visible plot window (plotted channels) or everything; `--export-csv FILE` writes everything after `--run-for`.
- **Plots (ImPlot):** linked x axes; a rolling window follows "now" while running; when paused the axes are free (wheel zoom, drag pan). Only the visible index range is drawn (binary search), min/max-decimated to about 2000 buckets per series so spikes survive zooming out.
- **Replay = re-simulation:** the run is deterministic, so a scrub back to time t is `reset()` (fresh DLL, same seed) plus stepping to t. No state snapshots are needed. A per-tick SHA-256 over (time, pose, wheel angles, slip angle) is the trajectory hash. The run record is maze hash + robot config file SHA-256 + firmware DLL SHA-256 + seed. Same record + same time = same trajectory hash; a different seed gives a different hash (unit-tested). The timeline slider shows a ghost robot at the recorded pose; "Rewind sim to cursor" makes it real.
- **Annotations (`sim/host/annotations`):** validated input (mms palette chars only, cells inside the maze, text clipped to 10 chars). Walls are stored once per segment (south/west map onto the neighbour's north/east), so a firmware that reports walls repeatedly cannot grow memory. Drawing: cell colours as semi-transparent fills; firmware text replaces the idle BFS distances; walls the firmware believes present are drawn over the truth (blue = right, amber = wrong; amber cross = real wall believed absent; red = not yet known).
- **Keyboard:** ImGui keyboard navigation is off. With it on, Space also "pressed" the focused button (a double toggle, a likely cause of the unreproduced Slice 5 stalls), and `WantCaptureKeyboard` was true whenever any window had focus. Shortcuts are gated by `!io.WantCaptureKeyboard`: Space, R, Ctrl+R (rescan + reload DLL), N (until next cell), Right (10 ms, Shift = 100 ms), +/- (speed 0.1x .. 64x, Max).
- **Layout:** Telemetry sits beside the maze when firmware is loaded; without firmware it is a tab next to Log, so the maze keeps the width the pixel checks need.
- **Not done:** motor current and battery channels (battery is constant in the model; current is not exposed by World yet).
- **Alternatives:** periodic state snapshots for instant scrubbing (more memory and a full World + firmware RAM snapshot; re-simulation is exact and costs at most ~4 s for 60 s in Debug); std::deque per channel (unbounded per-sample allocations).

## D10 — 2026-11-20 · mms stdio mode: lockstep bridge, physics motion executor (Slice 7)
- **Process (`sim/platform/process`):** Win32 `CreateProcessW` with three anonymous pipes (our ends non-inheritable), `CREATE_NO_WINDOW`, the child in a job object with `KILL_ON_JOB_CLOSE` (never outlives the simulator). stdout/stderr are read on two threads into bounded line queues (`\r\n` or `\n`). `read_line(0)` must not call `condition_variable::wait_for`: on MinGW even a 0 ms wait sleeps a timer slice (~15 ms), which made every tick 15 ms slow.
- **Protocol (`sim/host/mms_protocol`, `mms_bridge`):** semantics copied from mms `4ed1df48c522` source: annotation lines (`setWall`, `clearWall`, `setColor`, `clearColor`, `clearAllColor`, `setText`, `clearText`, `clearAllText`) apply at once, even during a move, and never answer; every other line is queued and executed in order. Invalid lines (wrong name, wrong token count, extra argument, unknown stat) get no answer and are counted. `wallX N` looks N-1 half-steps ahead with mms `isWall` rules (diagonals from a cell centre aim at a post). `moveForward N` that would hit a wall drives the allowable half-steps and answers `crash`; distance stats count the requested half-steps (as mms). Effective distance is `n > 2 ? n/2 + 1 : n` half-steps per move, a reset adds 15 to the next run, score = best eff + best turns + 0.1 (total eff + total turns), 2000 until solved, printed with `%g`.
- **Lockstep (`Session::load_mms`):** while the bridge is idle, each tick blocks until the solver's next command (think timeout 2 s headless, 500 ms in the GUI so the 2 s hang guard never fires); queries cost no simulated time, so runs are deterministic (equal trajectory hashes). A solver that misses the timeout is marked stalled and the simulation keeps running until it speaks again. Reset restarts the process.
- **Motion executor:** a sim-side controller on the true pose (the solver is not firmware): trapezoid profile (0.6 m/s, 3 m/s^2; turns 6 rad/s, 40 rad/s^2), absolute targets from the semi pose (errors do not accumulate, no snapping), feedforward from the motor constants (back-EMF, Coulomb, mass) + wheel-speed P, lateral correction by heading. Duty is capped by the World at `motor.max_voltage` (6 V on 2S). Doomed/blocked moves push into the wall until a real collision is recorded, then the mouse is placed at the allowable pose and answers `crash`.
- **Sensor walls (`--mms-walls sensors`):** front from the forward sensors at the cell centre; sides from side-looking sensors, or for 45 deg diagonals the minimum reading latched while they looked at the target cell's side walls on the way in. Anything the layout cannot see (after a turn, half steps, N > 1, diagonals) falls back to the truth and is counted (`sensor_fallbacks()`).
- **Tests:** `unit.mms` (label `mms`): stats/score by hand, isWall cases, toInt, every command incl. 14 malformed lines, annotations, motion accuracy (3 mm, 0.02 rad), crash at once / doomed, reset penalty, mid-move annotations, sensor walls, process pipes/exit code/kill, tiny flood-fill solver (deterministic twice) and upstream mms-cpp built unchanged from `external/mms-cpp` (`tools/fetch_mms_cpp.ps1`, gitignored).
- **Alternatives:** teleporting the mouse per command (mms itself; loses the physics, which is the point of this simulator); free-running wall-clock mode (non-deterministic runs).

## D11 — 2026-11-20 · mmsim-cli batch runner, session persistence, performance (Slice 8)
- **Batch (`sim/host/batch`, `sim/cli`):** one `Session` per maze on a pool of `--jobs` threads (atomic work index, results kept in input order). Worlds share nothing: each firmware load is a private DLL copy (own globals, own fiber per thread); each mms run its own solver process. Parallel and serial runs give identical trajectory hashes (tested). Firmware runs end at the `speed run done` or `ERROR` log line, a fault, a halt or `--max-sim-time`; mms runs when the solver exits. A run fails on: not solved, timeout, any crash (firmware: physical contacts; mms: `crash` replies), load error, fault, `ERROR` log. Exit code 0 / 1 (any failure) / 2 (usage). Globs: `*`/`?` in the file-name part, case-insensitive (PowerShell does not expand them). `--firmware demo` resolves a unique prefix in `firmware_bin`. `mmsim-cli` links statically.
- **Session persistence (`sim/app/settings`):** `mmsim.json` (maze, config, firmware or mms solver, wall source, seed, speed, boot buttons) and `imgui.ini` live in the data root, both gitignored (with `runs/` for Slice 9.2). Command-line arguments win; missing paths are skipped; a corrupt file only warns. Scripted runs (`--frames`/`--exit`) and `--no-session` neither read nor write them, so tests never create files.
- **Performance (Release, this PC, 12 logical CPUs):** physics-only tick 6.8-7.9 us (target <= 20 us); demo firmware 110x real time on one world (target >= 50x). 525 classic mazes with `--jobs 8`: 75 649 s simulated in 205 s, aggregate 369x; per world 47.5x under 8-way load (shared memory bandwidth/turbo), 21 us per tick including firmware. No optimisation was needed; nothing was changed for speed.
- **Classic set result (demo_floodfill, seed 1, 300 s limit):** 496/525 reached a speed run, 492 (93.7 %) crash-free (target >= 90 %). Failures are demo-firmware limits, not simulator faults: 13 time limits on long-search mazes (dame, diagonals, kilkai, killer, kyushu-2017, map-2, map-5, sunkai, torture, us93, vm2, wiggly1, zigzag); 18 runs with wall contacts (mostly followed by a wrong wall map and "target unreachable": e.g. japan1983 83 contacts, japan1991 10, alljapan-012-1991 10, uk2025-spring-classic 8); 2 "unreachable" without contact on `001`/`001-anomaly-test` (unusual files). Report: `build/classic.json` (not committed).
- **Alternatives:** a process per maze (isolation, but slower start and no shared loaded config); OpenMP (another dependency for a 20-line pool); storing settings in `%APPDATA%` (hidden from the user; the data-root files are easy to inspect and delete).

## D12 — 2026-11-20 · Slice 9 Wave 9A: pack model, motor current, analysis library
- **Battery (`RobotConfig::battery`, `World`):** per-motor armature current `I = (V - Ke G w) / R` every substep (`sim.i_l`, `sim.i_r`), pack current `I_bat = electronics_a + max(0, sum(duty * I))`, Coulomb-counted SoC (`sim.soc`, %), terminal voltage `sim.v_bat`. `battery.model` is **off by default**: the motors then see the ideal `battery_voltage_v` exactly as in Slices 3-8 (trajectory hashes and the 525-maze baseline are unchanged), while current and SoC are still integrated for the gauges. With `battery.model: true` the pack is `cells * OCV(SoC) - R_int * I_bat` (Neomouse `thermal_battery_sim.OCV` table) and the next substep's motor voltage is `duty * V_term`, clamped to `motor.max_voltage` without counting overvoltage events again (one substep = 250 us lag, no algebraic loop). The HAL `battery_voltage()` and the mms executor read the live terminal voltage. Keys: `battery.model`, `cells`, `capacity_mah`, `r_int_ohm`, `soc0`, `electronics_a`, `reset_v`.
- **Analysis (`sim/core/analysis/`, pure C++20, in `simcore`):** `maze_paths` (shortest_path, distance_field, potential_field), `trajectory` (compile_trajectory, straight_time), `metrics` (step_metrics, imu_stats, cornering, battery_health, Neomouse fault table + simulator fault cards, telemetry_events), `battery` (OCV, mission profile, battery_run, powers, junction_temps, live `ThermalEstimator`, axle loads, pitch limits), `runs` (run_series, compare_runs, motion_heatmap / bin_heatmap, run archive), `report` (offline HTML with inline SVG, MATLAB CSV `t_ms,segment,wheel_l_cps,wheel_r_cps,...` for `neomouse_pid_fit.m`).
- **Golden vectors:** `tools/gen_analysis_vectors.py` imports the Neomouse Python read-only and writes `tests/fixtures/analysis/*.json` (3 own seeded 16x16 mazes, one fully known and two partly known; 6 routes incl. U-turn / jump errors; 8 step cases; battery/thermal; 2 synthetic runs; heatmap; events). No mazefiles content. Dijkstra ties follow Python's heap order (cost, x, y, heading) and rounding is half-to-even, so paths, primitive texts and rounded numbers match exactly; 6578 assertions.
- **Run archive:** `runs/<yyyymmdd-hhmmss>_<maze>_<hash8>/run.json` + `telemetry.f32` (little-endian float32, channel-major; about 4x smaller than CSV, no zlib dependency). `runs/` is gitignored.
- **Alternatives:** porting by reading Python output at test time (needs Python in CI); a battery model always on (would change every existing run and the D11 baseline); zlib-compressed archives (new dependency for a few MB).

## D14 - 2026-11-20 · Interactive window fits the work area; dark native titlebar
- **Bug:** at 150 % DPI the window was `--size * scale` (1280x800 -> 1920x1200) centred on a 1920x1128 work area, so the titlebar sat above the screen top and Minimize / Maximize / Close were unreachable.
- **Fix:** interactive runs create the window hidden, then `ui::fit_window` (pure, unit-tested at 100/150/200 % and with oversized `--size`) fits the client area inside `SDL_GetDisplayUsableBounds` minus the native frame (`SDL_GetWindowBordersSize`, fallback 36/8/8/8), centres it, and maximizes when the request did not fit. Minimum size is 960x600 logical, capped to what fits. Scripted / `--hidden` runs keep the exact `--size` at scale 1, so pixel checks and captures are unchanged.
- **Titlebar:** `platform::apply_dark_titlebar` (new `mmsim_platform_window`, links `dwmapi`; Win32 stays in `sim/platform`, D6) sets `DWMWA_USE_IMMERSIVE_DARK_MODE` (20, fallback 19) and the Windows 11 caption colour `#0E1116`.
- **1280x720 logical** (150 % laptop work area): the top bar adds narrower tiers (combo with the full title -> combo with the short name -> one mode toggle instead of the Beginner/Engineer pair); sensor rows are tighter so all four fit.

## D15 - 2026-11-21 · Solver suite on a shared firmware stack
- **Structure:** `firmware/common/` (motion, control, sensors, map, mission in `solver.c`, planners in `plan.c`) is compiled into every `demo_*` DLL. A solver is a `solver_t` plus `fw_main`; the proven demo_floodfill behaviour is unchanged (UK 1987: search 42.2 s, return 34.0 s, speed run 20.7 s).
- **Costs:** 2 per cell, 5 per 90 degree turn (10 for a U-turn). Dijkstra and A* run over (cell, heading) states, so turns are priced. Tie-breaks are fixed, so runs stay deterministic.
- **A*:** the heuristic (Manhattan distance plus a turn lower bound) is admissible but not consistent, so nodes may be re-opened. The plan is kept until a newly seen wall blocks the remaining path: valid because unknown walls count as open in search mode.
- **Trémaux and the wall follower** only explore. After the goal, the way back and the speed run use the shortest path over the known cells. The wall follower detects a repeated (cell, heading) state and stops with `ERROR left-hand rule is looping`, so an island goal costs a log line, not an endless run.
- **Honest result:** Flood-Fill, Dijkstra and A* find the same speed-run route on every benchmark maze (within 0.4 s), so the speed run does not separate them. The way back is where they differ, and not systematically: on the generated loops maze the turn-weighted planners return in 31.9 s against 37.8 s for Flood-Fill, but on UK 1987 they take 40.1 s against 34.0 s. A sweep of the turn cost (2, 3, 5) moved A*'s UK 1987 return between 33.7 s and 40.2 s while Dijkstra stayed at 40.1 s, so the spread comes from which of several equal-cost routes is picked (tie-breaking) and from the cost model (5 per 90 degree turn) being a guess, not from the algorithms. Calibrating the costs against measured turn times is future work; the default stays at 5. Trémaux searches far longer on loop-rich mazes (UK 1987: 182.9 s).
- **Verification:** planner unit tests compare Dijkstra and A* with independent C++ references on 360 start states and 15 mazes; one integration test per solver; boundary, arm-check and determinism checks cover all five.
- **GUI:** the firmware menu shows human labels, solvers first, `test_*` fixtures last (Engineer mode only). `mmsim-cli --firmware dijkstra` accepts the short name.
- **Alternatives:** one DLL with a runtime algorithm switch (breaks "one folder, one firmware" and the hot-reload story); copying the stack into each folder (five copies of the control loop to keep in sync).


## D16 - 2026-11-22 · v0.2.0: per-user data, installer, help catalogue, config editor
- **Where data goes** (`resolve_data_paths`, unit-tested): `--root` or `--portable` / a `mmsim.portable` marker next to the exe keep state beside the exe (the zip); a dev checkout (CMakeLists.txt + firmware/ at the root) keeps writing into the repo; a `mmsim.installed` marker (written by Setup.exe) or an unwritable program folder selects `%LOCALAPPDATA%\MMSim\` (mmsim.json, imgui.ini, runs/, reports/, screenshots/, config/robots/). The installer never writes into the install folder after setup.
- **Installer:** Inno Setup 6, per-user (`PrivilegesRequired=lowest`, `{localappdata}\Programs\MMSim`, no UAC), Start Menu group, optional Desktop shortcut, Apps & Features uninstaller that asks before deleting `%LOCALAPPDATA%\MMSim` (silent uninstall keeps it). It packs the same staged folder as the portable zip (`tools/package_release.ps1`), minus `Launch_MMSim.bat` and `mmsim.portable`. CI builds both artefacts from one tag and publishes them with sha256 files.
- **Help text:** one X-macro catalogue (`help_text.def`) so every plot, gauge and technical control has a 1-2 sentence plain-English tooltip; a unit test checks length, ASCII and that every id used exists.
- **Config editor never overwrites** the bundled `generic_classic.json`: *Apply & Restart* rebuilds the session from the edited values, *Save Copy...* writes a new file under the user folder. Motor `max_voltage` above 6.0 V shows a warning (N20 on a 2S pack: duty = V / V_BAT, never 100 % PWM).
- **Compass:** bearing = wrap360(90 - theta), clockwise from north; the target tick is the firmware `hdg_target` channel (dir * 90).
- **Known cosmetic gap:** the VERSIONINFO block of mmsim.exe is overridden by the winpthread resource linked first; the icon resource is unaffected. Installer and Apps & Features show the right version.
- **Alternatives:** WiX/MSI (heavier, needs admin by default); NSIS (no good built-in modern wizard); always writing next to the exe (breaks under Program Files).
